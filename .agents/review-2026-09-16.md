# Code and dependency review — 2026-09-16–17

## Scope

Reviewed authentication boundaries, owned note/tag/attachment queries, Markdown and saved tasks, Kanban APIs and client state, encrypted backups and staged restoration, request validation, database migrations, and dependency compatibility. Existing unrelated CSS and documentation edits were preserved. All writes and verification used disposable local data; no production deployment or remote resource changes were made.

## Confirmed findings addressed

| Priority | Trigger and previous failure | Fix and regression coverage |
| --- | --- | --- |
| P1 | Concurrent attachment requests reused the same R2 key. A delayed retry could overwrite the winning bytes, or delete them after an ID conflict. | Each attempt gets a unique object. D1 chooses the winner, matching retries return its metadata, and losing objects are removed. Tests exercise both matching and conflicting sizes against the actual migrations, D1, and R2. Drizzle-wrapped constraint causes now produce `409`. |
| P1 | A staged backup upload begun before finalization could finish later and overwrite the now-live attachment. | Conditional R2 writes preserve the first exact-size object. A controlled delayed-upload test finalizes the competing upload before releasing the stale request and verifies the original bytes survive. |
| P1 | A task toggle read old Markdown, then overwrote a concurrent content edit and rebuilt tags from the old note. | Compare source content in the atomic update, gate tag synchronization on the saved content, and return `409` when the source changed. Regression coverage verifies both the newer text and its tag relations remain intact. |
| P2 | `GET /api/notes?limit=100` bound 100 IDs plus a user ID, exceeding D1's parameter limit. | JSON-bound ID sets keep both attachment and tag hydration queries within the limit. A real local D1 test retrieves all 100 notes. |
| P2 | Kanban allowed 10,000-character descriptions but rejected valid Chinese text above a 12 KiB JSON request cap. | Shared character limits and a byte budget that covers Unicode/JSON escapes. API tests create and update full-length Chinese descriptions and reject over-limit descriptions. |
| P2 | The Node platform proxy committed a short R2 body before reporting its size mismatch. | Validate size on stream completion before writing buffered data; preserve typed size errors in Workers. Tests cover short/long/exact bodies and conditional writes in both Node and actual Workers `FixedLengthStream` execution. |
| P2 | Appending pages kept every Markdown body and mounted every note/media component, so DOM and retained body memory grew with the entire visited notebook. | Measured virtual rows, automatic next-page loading, and a count/byte-bounded LRU body cache. An owned batch API restores evicted bodies; focused controls and active interactions remain mounted. Cache and D1 boundary tests cover eviction, large bodies, request order, authorization, and the 100-ID limit. |

The upgraded Zod also accepts allowed supplementary-Unicode filenames in backup manifests. A 180-emoji filename now passes an encrypted export/import round trip; no custom filename validator was necessary.

## Long-list verification — September 17

The final production build was served by local Wrangler/Workers and exercised with headless Chrome against a disposable D1 account containing 3,000 notes, including 429 roughly 104 KiB Markdown documents. The browser loaded all 100 pages, returned to evicted records, and resized from 1440×1000 desktop to 390×844 mobile. Desktop light/dark and mobile dark screenshots were inspected; no overflow or browser runtime errors occurred.

| Measurement | Result |
| --- | --- |
| Mounted note cards | 8 initially, 20 at the end, 22 maximum during traversal, 5 on mobile |
| DOM elements | 462 initially, 770 at the end, 369 on mobile |
| JS heap after forced GC | 4.53 MiB initially, 12.14 MiB after 3,000 notes, 12.13 MiB after returning to the top, 12.21 MiB on mobile |
| Continuous scroll, 175 measured frames | p95 21.0 ms, maximum 23.7 ms, zero frames above 50 ms |

The measurements describe this local Chrome run, not low-end-device or production-load guarantees. Full DTOs have a soft 180-record / estimated 16 MiB budget, with explicit exceptions for visible and active records. Loaded IDs and geometry remain proportional to the visited feed. Server search remains a substring scan and pagination remains offset-based.

A separate final-browser interaction pass injects an append failure and slow body reads. It verifies that existing cards survive errors, retries recover the failed page, and rapid scrolling never has more than one body-restoration request in flight. Rehydrated tasks persist through the real API, menu keyboard navigation restores focus without scrolling, real R2 audio keeps playing outside the viewport and through Notes/Kanban switches, and full-library search plus editing a formerly unloaded note succeed. The completed pass reports no runtime errors.

Artifacts and reproducible local browser scripts are ignored under `output/performance/`. The disposable account, session, notes, audio attachment, and generated cookie/seed files were removed after verification. The final run used a cleanly restarted Worker: rebuilding while an older preview process was live had briefly mixed SvelteKit build identifiers and caused client startup failure. This was resolved by restarting the preview with the completed build.
